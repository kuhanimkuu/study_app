# Study OS — HTTP server

Exposes the engines under `features/` over HTTP. This is the server-hosted
backend side of the project's architecture (see the top-level `README.md`'s
"Architecture note" for why: Chaquopy can't embed PyMuPDF/Tesseract on
Android, so the Flutter app is a thin client instead of embedding Python).

## Architecture note: local-first data

This server is intentionally "dumb" about user content. `server/db.py`'s
`users` table stores ONLY auth essentials (email, password_hash,
display_name) plus a per-user AES-256-GCM key (`server/crypto.py`) — never
chat history, progress, or BYOK API keys at rest. The Flutter client is the
source of truth for all of that:

- **Chat history / activity log** — lives in the client's own on-device
  database (`frontend/lib/core/storage/local_db.dart`). There is
  deliberately no `/api/history` endpoint.
- **BYOK model preference** (backend, model name, API key) — lives in the
  client's OS keystore (`frontend/lib/core/settings/model_settings_service.dart`).
  `/api/account` only ever holds `display_name`.
- **Per-request use** — when a request actually needs client-held data, the
  client sends it along on that one call and the server never persists it:
  `local_events` on `/api/ask/text` (the client's own activity log, so the
  moderator's `memory_query` route can answer "what did I struggle with"
  without the server keeping a copy), and `model_config.encrypted_api_key`
  (the BYOK key, AES-GCM-encrypted client-side with the user's own
  `encryption_key` — see `routers/ask.py`'s `ModelConfig` and
  `frontend/lib/core/crypto/user_crypto.dart`, which must match
  `crypto.py`'s wire format exactly; verified via a real bidirectional
  round-trip test, see `frontend/test/user_crypto_test.dart`).

Signup and login are the only two calls that ever return `encryption_key`
(`db.auth_user()`) — the device needs it once to persist it locally.
Returning it again on every login (not just signup) lets a reinstalled app
recover access to previously-encrypted local data.

**Projects are the one deliberate exception** to "server stores nothing of
the user's own content" — see `db.py`'s module docstring. A project's
material has to be embedded (`rag/indexing`, via `fastembed`) to be
searchable, and that compute already happens here, so the resulting index
naturally lives where it was computed. `server/db.py`'s `projects` table
only holds each project's identity (id/slug/display name/owner, scoped
per-user so two users' identically-named projects never collide); the
actual indexed material stays in JSON files under
`rag/projects/projects/user_<id>/` (see `routers/projects.py` and
`moderator/engine.py`'s `_user_projects_dir`).

## Run it

```
pip install fastapi uvicorn python-multipart
uvicorn server.main:app --reload --port 8000
```

Interactive API docs (auto-generated by FastAPI): `http://127.0.0.1:8000/docs`

## Endpoints

| Endpoint | Method | Body | Notes |
|---|---|---|---|
| `/api/health` | GET | — | liveness check |
| `/api/auth/signup` | POST | JSON `{email, password, display_name?}` | returns `{token, user}` — `user` includes `encryption_key` (only time besides login) |
| `/api/auth/login` | POST | JSON `{email, password}` | returns `{token, user}`, `encryption_key` included again |
| `/api/auth/me` | GET | — (auth required) | current user's public profile — no `encryption_key` |
| `/api/account` | GET/PATCH | PATCH: JSON `{display_name?}` | display name only — BYOK settings are NOT server state, see Architecture note above |
| `/api/projects` | GET/POST | POST: JSON `{display_name}` | create/list the current user's projects; POST returns `{id, slug, display_name, created_at}`, GET returns `{projects: [...]}` with each also carrying `chunk_count` |
| `/api/projects/{slug}` | DELETE | — | deletes the project row and its stored material |
| `/api/projects/{slug}/material` | POST | multipart `text?` or `file?` (.pdf/.txt) | indexes the given material into the project via `rag/projects`; returns `{project, status, chunks}` — `status` is `"created"` or `"updated"` (accumulates across calls, doesn't replace) |
| `/api/projects/{slug}/studio` | GET/POST | POST: JSON `{doc_type, title?}` | generate ("study_guide"/"revision_notes"/"summary"/"formula_sheet"/"worksheet"/"flashcards"/"practice_exam"/"lab_report") or list documents generated from the project's material via `document_generation/generate_docs`; POST returns `{id, doc_type, title, url, created_at}`, GET returns `{artifacts: [...]}` |
| `/api/projects/{slug}/studio/{artifact_id}` | DELETE | — | deletes the artifact's DB row and its PDF file |
| `/api/ask/text` | POST | JSON `{content, task?, requested_format?, params?, model_config?, local_events?, session_id?}` | `params` carries structured arguments for the moderator's explicit-task-only routes (see `moderator/README.md`'s "Structured routes" table); `model_config` is `{backend, model_name?, encrypted_api_key?}` (omit or `backend: "local"` for the server's built-in model); `local_events` is the client's own activity log, forwarded to the `memory_query` route |
| `/api/ask/image` | POST | multipart `file`, form `session_id?` | routes through the full quality→enhancement→content_identification→OCR/vision pipeline, not just plain OCR |
| `/api/ask/pdf` | POST | multipart `file?`, form `query?`, `session_id?` | `file` required on the first call in a session; a follow-up call only needs `query` (see below) |
| `/api/ask/audio` | POST | multipart `file`, form `session_id?` | transcribes (`faster-whisper`), then routes as text |
| `/api/ask/web` | POST | JSON `{url, kind?, session_id?}` | fetches and returns raw content — NOT routed through the moderator, see Notes |
| `/api/ask/project` | POST | JSON `{content?, project?, query?, session_id?}` | mirrors `/api/ask/pdf`'s shape: name a project first (no query) -> clarification, then `query` in a follow-up call |
| `/generated/<file>` | GET | — | static file serving for artifacts the moderator's structured routes produce (images, GIFs, GLB models, PDFs) — see Notes |

Every `/api/ask/*`, `/api/account`, and `/api/projects*` endpoint requires a JWT bearer token (`Authorization: Bearer <token>` from signup/login). All `/api/ask/*` endpoints except `/web` return the moderator's `{"blocks": [...], "session_id": ...}` shape.

## Notes

- Each `/api/ask/*` endpoint does exactly two things: run the matching `input_pipeline` engine to normalize the input, then call the moderator. No classification logic lives in this file — that's the input engines' job, per `PATHWAY.md`'s architecture.
- **Uploaded files are saved to `server/uploads/<session_id>/`, not a temp dir that gets deleted after the request.** The moderator's clarification loop is a genuine multi-turn conversation (upload a PDF -> "what would you like me to do with it?" -> "search for X") — a follow-up call needs the file still on disk. `server/uploads/` is gitignored (runtime artifact, not source) and currently never cleaned up automatically — worth adding retention/cleanup before any real deployment.
- **`/generated/<file>` serves `features/moderator/generated/`** (mounted via FastAPI's `StaticFiles`), the directory `moderator/engine.py`'s structured routes (`static_image`, `animation`, `interactive_3d`, `generate_doc`) write their output files to. A block's `content` for these types is a `/generated/<file>` URL path, not a bare local filename — the client builds the fetchable URL as `base_url + content`. **This was a real gap found and fixed after wiring those routes in:** the first version returned server-local filesystem paths a Flutter client could never actually fetch; verified fixed with a real `curl` round-trip (generate an image via `/api/ask/text`, then `curl` the returned `/generated/...` URL and confirm it's a real 22.6KB `image/png`).
- **`/api/ask/pdf`'s and `/api/ask/project`'s two-call flows are real and tested, not just designed:** first call (upload/name) gets back a `clarification`; the follow-up call sends only `query` and the moderator resumes using state it stored from the first call. The PDF version surfaced a real bug — the clarification context didn't originally store `pdf_path`, so the resume would have silently failed; see `moderator/README.md`.
- **`/api/ask/web` bypasses the moderator entirely, on purpose** — the moderator has no web-content route implemented, so pretending it "understands" fetched web content would produce a confusing wrong answer most of the time. This endpoint just returns the fetched content as a `source` block instead of faking understanding.
- **Dev-permissive CORS** (`allow_origins=["*"]`) — fine for local development against a Flutter client, must be tightened to specific origins before any real deployment.
- **Tested end-to-end for every endpoint against a real running server** (not just direct Python calls): text (including the newly-added `params` field for structured tasks — verified `numeric_stats` returns exact matching values), image upload (full pipeline), PDF upload/follow-up, project name/follow-up, web fetch, a full voice pipeline (synthesized speech -> Whisper -> spoken-math normalization -> symbolic solve -> LLM explanation, which surfaced and fixed a second real bug: spoken words like `"plus"`/`"equals"` weren't recognized as math — fixed in `moderator/engine.py` and `text_input/engine.py`), and the `/generated` file-serving round-trip described above.
