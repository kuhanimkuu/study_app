## Decisions that override the blueprint

- **Hosting/DB (2026-09-14):** HelioHost deployment uses **PostgreSQL**, not SQLite. The app is **not offline-capable** — always requires connectivity. This overrides Section 30 ("Local-First Architecture") and the SQLite-first framing in Section 32 ("Database Strategy") of the blueprint. Local-first/sync-engine architecture is not the plan.

- **`study_os_overview-v2.pdf` is product/UX vision only, not an infra spec (2026-09-14):** This earlier project doc describes a fully local-first, on-device architecture — Python embedded in the Android app via Chaquopy, LLM inference via a native llama.cpp build on-device, SQLite as the source of truth, offline-capable for everything except web research, and a centralized backend as a later optional addition for accounts/sync. User explicitly confirmed the already-built server+Postgres, always-online architecture (above) is the correct one — **the code is the source of truth, not this document.** The doc's product/UX ideas (single-prompt home screen, quick actions, Study Modes, the block-rendering contract) remain useful references for frontend design, since they map closely onto what's already implemented server-side (the `Block` schema already covers text/equation/interactive_graph/diagram/animation/3d/pdf/source/table); its infrastructure sections (§2, §22, §27, §30, §35 — Chaquopy, on-device llama.cpp, offline-first, SQLite, APK bundling) do not apply and should not inform backend or deployment decisions.

### 2026-09-17 — DONE: first real deployment (Render, temporary stand-in for HelioHost)
User asked for something to temporarily host the backend before setting up HelioHost. Tried Railway first (CLI already installed, user logged in), but their trial had expired and it demanded a paid plan before creating anything — switched to Render per the user's choice, which has a real no-payment-method free tier.

**Repo changes to make the backend hostable at all**:
- `server/core/security.py`: the JWT signing secret now reads `JWT_SECRET` from the environment first, falling back to the local gitignored auto-generated file only when unset. Required on any host with an ephemeral filesystem (Render's container) — regenerating the secret on every restart would silently invalidate every existing session.
- `server/core/config.py`: `Settings.database_url` now normalizes a plain `postgresql://` connection string (what Render/Railway/any managed-Postgres `DATABASE_URL` reference actually hands you) to `postgresql+asyncpg://` automatically, instead of requiring every hosting provider's env var to already know this app's driver choice.
- New `render.yaml` (Blueprint: a `study-os-backend` web service + a free `study-os-db` Postgres, `JWT_SECRET` set via Render's `generateValue`, `GOOGLE_OAUTH_CLIENT_ID` carried over from `.env`) and a `Procfile`, committed to the repo root.

**A real deploy-time bug found and fixed**: the `b5ee5d199c84` migration ("add ON DELETE CASCADE to all domain foreign keys") dropped each foreign key by a **hardcoded name it assumed Postgres would auto-generate** (`<table>_<column>_fkey`) for the previous migration's unnamed `ForeignKeyConstraint`. That assumption happened to hold on this project's own local Postgres (verified empirically in an isolated scratch schema, not the app's real data) but not on Render's fresh database, where the actual name Postgres assigned didn't match — the first deploy got through the first two migrations, then failed the whole chain with `UndefinedObjectError` on `concepts_knowledge_space_id_fkey`. Rewritten to look the real current constraint name up from `information_schema` at migration-run time instead of assuming one, so it's correct on any fresh Postgres host regardless of exactly how it named an unnamed constraint; `downgrade()` now recreates the FK unnamed too, rather than assuming the same old implicit name back. Full backend test suite (91) still passes; the fix was verified by reproducing the exact create-unnamed-FK → lookup → drop → recreate-with-cascade sequence against a throwaway schema on the real local Postgres before pushing.

**What's actually live**: `https://study-os-backend-iik8.onrender.com` — verified reachable (`GET /api/health` → `{"status":"ok"}`) and hitting real Postgres (a login attempt against a nonexistent email returned the real "invalid email or password" response, not a stub). `frontend/lib/core/api/default_base_url.dart` now points here by default on every platform (replacing the old per-platform `127.0.0.1`/`10.0.2.2` localhost defaults) — still editable in-app via the server settings dialog for local dev. Rebuilt and installed on the user's real phone.

**Known limitations of this temporary host** (not gaps to close now — this is explicitly a stopgap before HelioHost): Render's free web service spins down after 15 min idle (slow first request after that); the free Postgres expires after 90 days; no persistent volume is attached, so the RAG project-chunk JSON files and any `/uploads`/`/generated` artifacts on disk won't survive a redeploy (Postgres-backed data is unaffected); the local-model backend path (torch/transformers) may be too heavy for the free instance's memory — BYOK (Anthropic/OpenAI) chat and everything else should be unaffected either way; `CORS_ALLOWED_ORIGINS` is left at `*` for this temporary host.
